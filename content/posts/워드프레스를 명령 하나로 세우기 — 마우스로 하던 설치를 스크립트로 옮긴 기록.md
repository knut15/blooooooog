워드프레스를 두 번째로 깔면서 알았다. 첫 설치에 30분이 걸렸는데, 다시 깔 때도 똑같이 30분이 걸린다. 그사이 배운 게 하나도 남지 않는다. 테마를 뭘 골랐는지, 퍼머링크를 어떻게 잡았는지, 어떤 플러그인을 껐는지 — 전부 머릿속에만 있고 기억은 흐려진다.

그래서 설치 과정을 파일 하나로 옮겼다. `./setup-local.sh` 한 줄이면 PHP도, 데이터베이스도, 워드프레스도, 테마와 플러그인까지 자리를 잡는다. 여기까지 오는 데 세 군데서 막혔다. 그 세 군데가 이 글의 알맹이다.

## 1. 마우스로 하는 일에는 기록이 남지 않는다

관리자 화면에서 하는 설치는 편하다. 검색창에 테마 이름을 넣고 설치를 누르고 활성화를 누른다. 문제는 그다음이다.

- 반년 뒤에 같은 환경을 다시 만들 때 무엇을 어떤 순서로 눌렀는지 기억나지 않는다
- 서버를 옮기면 처음부터 다시 클릭한다
- 어딘가 하나를 빠뜨려도 눈치채지 못한다. 빠뜨렸다는 사실 자체가 기록되지 않으니까

설치를 스크립트로 옮기면 이 셋이 한 번에 사라진다. 무엇을 했는지가 파일에 남고, 그 파일을 다시 돌리면 같은 결과가 나온다.

## 2. wp-cli — 관리자 화면과 같은 일을 명령으로

워드프레스에는 `wp-cli`라는 공식 도구가 있다. 관리자 화면에서 마우스로 하던 일을 명령 한 줄로 한다.

> 🚗 **비유**: 은행 업무를 창구에서 볼 수도 있고 앱으로 볼 수도 있다. 할 수 있는 일은 같다. 창구는 직원이 안내해주니 처음엔 편하고 앱은 익숙해지면 훨씬 빠르다. `wp-cli`가 앱 쪽이다.

테마 하나를 까는 일을 비교하면 이렇다.

| | 관리자 화면 | wp-cli |
| --- | --- | --- |
| 방법 | 외모 → 테마 → 새로 추가 → 검색 → 설치 → 활성화 | `wp theme install generatepress --activate` |
| 클릭 수 | 6번 | 0번 |
| 기록 | 남지 않음 | 파일에 한 줄로 남음 |

스크립트에서 실제로 쓴 부분이다.

```bash
$WP theme install generatepress --activate
$WP plugin install seo-by-rank-math --activate
$WP plugin install ad-inserter --activate
```

설정도 마찬가지다. 설정 화면을 돌아다니는 대신 이렇게 적는다.

```bash
$WP option update timezone_string 'Asia/Seoul'
$WP rewrite structure '/%category%/%postname%/' --hard
```

이 두 줄은 "시간대를 서울로 맞추고, 글 주소를 `/카테고리/글제목/` 형태로 쓴다"는 뜻이다. 화면에서 찾아 들어가면 각각 다른 메뉴에 있다.

## 3. 두 번 돌려도 망가지지 않게

스크립트를 쓸 때 가장 신경 쓴 부분이다. 설치 중간에 인터넷이 끊기거나 오타를 냈을 때, 처음부터 다시 돌려도 아무 일이 없어야 한다.

> 🚗 **비유**: 엘리베이터 버튼을 이미 눌렀는데 한 번 더 누른다고 엘리베이터가 두 대 오지는 않는다. 이미 눌린 상태면 그냥 그대로다.

이 성질을 **멱등성**이라고 부른다. 같은 일을 몇 번 시켜도 결과가 한 번 시킨 것과 같다는 뜻이다.

만드는 방법은 단순하다. 무언가를 하기 전에 이미 되어 있는지 먼저 본다.

```bash
if [ ! -f "$WP_DIR/wp-load.php" ]; then
  $WP core download --locale=ko_KR
fi
```

`wp-load.php`는 워드프레스 코어가 풀리면 생기는 파일이다. 그게 있으면 이미 받았다는 뜻이니 건너뛴다. 설치 여부도 워드프레스에게 직접 물어본다.

```bash
if ! $WP core is-installed 2>/dev/null; then
  $WP core install --url="$WP_URL" ...
fi
```

덕분에 "어디까지 했더라"를 기억할 필요가 없다. 막히면 고치고 처음부터 다시 돌리면 된다.

## 4. 막힌 곳 셋

여기서부터가 실제로 시간을 쓴 부분이다.

### 데이터베이스가 문을 안 열어준다

첫 실행에서 이 메시지가 나왔다.

```
ERROR 1698 (28000): Access denied for user 'root'@'localhost'
```

비밀번호가 틀렸다는 뜻으로 읽히지만 아니었다. 비밀번호를 물어보지도 않았다.

Homebrew로 설치한 MariaDB의 `root` 계정은 **비밀번호 대신 컴퓨터 사용자 계정으로 신원을 확인한다.** `unix_socket` 인증이라고 부른다.

> 🚗 **비유**: 아파트 경비실이 비밀번호를 묻지 않고 얼굴을 본다. 등록된 얼굴이면 들여보낸다. 아니면 비밀번호를 아무리 잘 대도 못 들어간다.

데이터베이스의 `root`는 "이 컴퓨터의 `root` 사용자"만 받아들이도록 되어 있었다. 내 계정 이름은 `kim`이라 거부당한 것이다.

확인해보니 설치 과정에서 `kim` 이름의 데이터베이스 계정이 이미 만들어져 있었다. 모든 권한도 갖고 있었다.

```
GRANT ALL PRIVILEGES ON *.* TO `kim`@`localhost` ... WITH GRANT OPTION
```

그래서 `mysql -u root` 를 `mysql` 로 바꿨다. 사용자를 지정하지 않으면 현재 컴퓨터 계정으로 접속한다. 한 단어를 지운 것이 해결책이었다.

### 압축을 풀다가 죽는다

다음은 이 오류였다.

```
PHP Fatal error: Allowed memory size of 134217728 bytes exhausted
```

134217728 바이트는 128MB다. PHP는 프로그램 하나가 쓸 수 있는 메모리에 상한을 둔다.

> 🚗 **비유**: 책상이 작으면 큰 도면을 펼칠 수 없다. 도면이 잘못된 게 아니라 책상이 좁은 것이다.

워드프레스 압축 파일 안에는 파일이 수천 개 들어 있다. 그걸 한꺼번에 푸는 동안 128MB로는 모자랐다.

고치는 방법은 두 가지다. `php.ini` 설정 파일을 열어 상한을 올리거나, **그 명령을 실행할 때만** 올리거나.

```bash
WP="php -d memory_limit=512M $ROOT/bin/wp.phar --path=$WP_DIR"
```

`-d memory_limit=512M` 은 이 명령에만 붙는다. 설정 파일은 건드리지 않았다. 컴퓨터의 다른 PHP 프로그램은 영향을 받지 않는다.

### 글 주소가 전부 404

설치는 끝났고 첫 화면도 떴는데, 글을 누르면 404가 떴다.

워드프레스의 글 주소는 실제 파일이 아니다. `/미분류/글제목/` 이라는 주소에 해당하는 폴더나 파일은 서버 어디에도 없다.

> 🚗 **비유**: 아파트에 "3층 김씨댁"이라고 적힌 우편함은 없다. 편지는 관리실이 다 받아서 "3층 김씨댁이면 302호구나" 하고 나눠준다.

워드프레스에서 그 관리실 역할을 하는 것이 `index.php` 하나다. 모든 요청을 이 파일이 받아서 주소를 해석하고 알맞은 글을 찾아준다. Apache나 nginx 같은 정식 웹서버는 "없는 주소는 전부 `index.php`로 보내라"는 규칙을 알고 있다. 워드프레스가 만들어주는 `.htaccess` 파일에 그 내용이 들어 있다.

그런데 개발용으로 쓴 PHP 내장 서버에는 그 규칙이 없다. 주소에 해당하는 파일을 찾다가 없으면 그냥 404를 돌려준다.

그래서 관리실 역할을 하는 파일을 열 줄로 만들었다.

```php
<?php
// PHP 내장 서버에서 WordPress 퍼머링크를 동작시키는 라우터
$root = __DIR__ . '/wordpress';
$path = parse_url( $_SERVER['REQUEST_URI'], PHP_URL_PATH );
$file = $root . $path;
if ( $path !== '/' && file_exists( $file ) && ! is_dir( $file ) ) {
    return false; // 실제 파일은 그대로 서빙
}
$_SERVER['SCRIPT_NAME'] = '/index.php';
require $root . '/index.php';
```

읽는 순서는 이렇다. 요청이 들어오면 그 주소에 진짜 파일이 있는지 먼저 본다. 이미지나 CSS처럼 실제로 존재하는 파일이면 그대로 내보낸다(`return false`). 그런 파일이 없으면 워드프레스의 `index.php` 에 넘긴다.

서버를 띄울 때 이 파일을 마지막 인자로 준다.

```bash
php -S localhost:8080 -t "$ROOT/wordpress" "$ROOT/router.php"
```

## 5. 대가

이 방식이 공짜는 아니다.

**로컬 환경이 실서버와 다르다.** PHP 내장 서버는 개발용이라 동시 접속을 견디지 못한다. 실서버에서는 nginx와 PHP-FPM을 쓰게 된다. 그러면 `router.php` 는 필요 없어지는 대신 nginx 설정이 필요하다. 로컬에서 잘 돌던 것이 서버에서 다르게 동작할 여지가 남는다.

**스크립트가 이 컴퓨터에 묶여 있다.** 경로가 `/opt/homebrew` 로 고정되어 있어 Apple Silicon 맥에서만 그대로 돈다. Intel 맥은 `/usr/local` 이고 리눅스는 구조가 아예 다르다.

**관리할 것이 하나 늘었다.** 워드프레스만 관리하면 됐는데 이제 스크립트도 관리한다. 워드프레스가 바뀌면 스크립트도 손봐야 한다.

그럼에도 옮긴 이유는 하나다. **두 번째부터는 30분이 1분이 된다.** 그리고 무엇을 왜 그렇게 설정했는지가 파일에 남는다.

## 6. 남은 것

지금 스크립트가 하는 일을 정리하면 이렇다.

| 단계 | 하는 일 |
| --- | --- |
| 1 | 비밀번호를 무작위로 만들어 `.env` 에 넣는다 (최초 1회) |
| 2 | MariaDB를 켜고 응답할 때까지 기다린다 |
| 3 | 데이터베이스와 전용 계정을 만든다 |
| 4 | 워드프레스 코어를 한국어판으로 받는다 |
| 5 | `wp-config.php` 를 만든다 (파일 편집 차단, 리비전 5개 제한) |
| 6 | 워드프레스를 설치한다 |
| 7 | 시간대·날짜 형식·퍼머링크를 잡는다 |
| 8 | 기본 샘플 글과 안 쓰는 테마·플러그인을 지운다 |
| 9 | 테마를 깔고 활성화한다 |
| 10 | 플러그인을 깔고 활성화한다 |
| 11 | `ads.txt` 자리를 만들어 둔다 |

아직 안 한 것도 있다. 실서버용 설치 스크립트는 따로 만들어야 한다. macOS 밖에서도 도는지는 확인하지 않았다.

한 가지는 처음부터 정해두길 권한다. **비밀번호가 든 `.env` 파일은 저장소에 올리지 않는다.** 스크립트가 무작위로 만들어 넣기 때문에 파일만 빼면 된다. 대신 어떤 항목이 필요한지 적은 `.env.example` 을 올려두면 다음 사람이 형식을 알 수 있다.
